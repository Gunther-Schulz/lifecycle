**A. RECORDS MANAGEMENT / ARCHIVAL SCIENCE**
1. Disposition schedule per record class (ISO 15489) → maps to per-class staleness+exit policy: each entry-KIND declares its own retention rule, not one global TTL. VERIFIED (CASRAI ISO 15489 guide; California SOS records handbook).
2. Appraisal as a RECURRING process (ISO 15489:2016 embeds appraisal at multiple points, not a one-shot gate) → maps to admission: re-evaluated over an entry's life, not decided once at write time. VERIFIED (search-result synthesis of ISO 15489-1:2016 concepts).
3. Records continuum model (Upward/McKemmish, Australian archival theory) → rejects staged lifecycle; record-keeping is one continuous, multi-dimensional process (create/capture/organize/pluralize happening at once) → maps to: don't model staleness/exit as one-way linear stages — treat an entry as always "in becoming," re-contextualized by later use. VERIFIED (Wikipedia "Records continuum model"; SAA glossary; AIIM blog on the lifecycle-vs-continuum divide, which is a live, unresolved practitioner debate — not a settled answer).
4. Vital/essential records designation (NARA) → a protection class: entries marked load-bearing-for-continuity are exempted from ordinary disposition and get extra duplication/priority. VERIFIED (NARA Essential Records Guide, archives.gov).

Degenerate forms: retention schedules go **shelf-ware** — "static schedules quickly become compliance liabilities," enforcement responsibility diffuses across legal/IT/compliance with no owner, audits find policy-exists ≠ policy-followed (VERIFIED, AccessCorp/records-audit sources; 2025 report: ~$238.5M in fines from record-keeping/retention failures). The lifecycle model's OWN degenerate form is exactly what the continuum model was built to fix: rigid stage boundaries that don't reflect how records actually get reused. No documented degenerate form found for vital-records designation specifically — mark that mapping PARAMETRIC.

**B. DATA GOVERNANCE / CMDB**
1. Golden record + survivorship rules (DAMA/MDM) → maps to derived-fact re-derivation: a fact merged from multiple sources via explicit match/survivorship logic, marked authoritative, recomputed when a source value changes. VERIFIED (DAMA def via Profisee/Semarchy/dnb.com).
2. Data lineage → maps to the basis/kill-condition chain: recorded provenance from source to derived fact, read to decide what invalidates when upstream moves. VERIFIED (Wikipedia "Data lineage").
3. Data stewardship role → maps to a named writer/reader per data domain, accountable over TIME, not just at creation. VERIFIED (TechTarget, OvalEdge).
4. Timeliness as its own data-quality dimension, distinct from accuracy/completeness/consistency → maps to an explicit staleness measure our layer should score separately, since a fact can be accurate but not current. VERIFIED (standard DQ-dimension framing, multiple sources).

Degenerate forms: stewardship as **title without behavior** — "dubbing people as stewards... rather than cultivating behaviors of stewardship"; only 43% of orgs report successful stewardship efforts (Gartner CDAO 2024 survey, via Dataversity/OvalEdge — VERIFIED); "a steward without authority to challenge data quality issues isn't performing governance, they're performing documentation." Golden-record degenerate form not documented in what I read — one source argues the golden-record model itself is now being questioned for AI-agent consumption ("golden record → golden context"), but that's a live reframing, not a named failure mode — PARAMETRIC.

**C. CACHE / DERIVATION THEORY**
1. TTL vs event-driven invalidation → maps directly to two staleness-trigger types our layer needs per entry class: a decay clock (TTL) vs an upstream-write trigger (event-driven, tighter but couples the writer to every dependent). VERIFIED (multiple cache-strategy sources; concrete numbers cited: 5-60min TTL for static/95%+ hit rate, 1-10s for dynamic — these read as convention/rule-of-thumb rather than derived from actual staleness tolerance, i.e. TTL selection is commonly cargo-culted — INFERRED from the sources' own framing, not a named practitioner postmortem).
2. Stale-while-revalidate → maps to a graceful-degradation READ pattern: serve the stale entry now, refresh in the background — decouples "fresh enough to read" from "fresh enough to block on." VERIFIED (systemoverflow.com, oneuptime.com).
3. Incremental materialized-view maintenance (Gupta & Mumick, "Maintaining Views Incrementally," SIGMOD 1993) → the formal answer to "derived facts re-derived when upstream moves": a counting algorithm tracks per-tuple derivation counts so a view updates from a DELTA to the base data, without re-accessing the view or the whole source. VERIFIED (ACM SIGMOD Record 1993; multiple citations).
4. "There are only two hard things in CS: cache invalidation and naming things" (Phil Karlton, informal) → the reason it's hard is structural: correctness requires knowing every CONSUMER of a value and every EVENT that changes its truth — an argument for explicit dependency edges over implicit trust. PARAMETRIC/informal attribution, widely cited, no primary source found.

Degenerate forms: TTL cargo-culting as above (INFERRED, not a named postmortem). Event-driven invalidation's own failure mode, standard in the cache literature but not tied to a single named incident here: incomplete pub/sub wiring makes an entry invisibly staler than a naive TTL cache would ever allow, because nothing ever expires it on its own — PARAMETRIC.

**D. DELIBERATE FORGETTING**
1. Adaptive/functional forgetting (forgetting as a mechanism that supports generalization and reduces interference, not a failure) → the theoretical case for aggressive, first-class pruning rather than pruning as mere resource management. VERIFIED (PMC "Computational Constraints in Cognitive Theories of Forgetting"; arxiv 2601.09726 "Forgetting as a Feature").
2. Interference-based forgetting (competing memories displace each other) vs pure time-decay → maps to: our layer's kill trigger should be a CONTRADICTING write, not an elapsed-time clock — matches this corpus's own existing stance (evidence-gated re-derivation fires on new evidence, not age). VERIFIED (PMC "Forgetting to Remember: decay and interference," Purdue).
3. Spacing effect / retrieval practice ("testing effect") → maps to access-triggered strengthening: an entry that gets re-read/re-confirmed should have its staleness clock reset or extended, i.e. revalidate-on-read as a retention mechanism, not just a caching optimization. VERIFIED (multiple meta-analyses; robust, thousands of replications).
4. Encoding-competition result ("survival of the fittest," PMC6357916): higher interference AT ENCODING produces fewer but more robust memory traces → maps to: a strict admission gate (only contested/cross-checked facts get in) yields a smaller, more durable persisted set than admitting everything uncontested. VERIFIED (PMC6357916).

Degenerate form note: this axis is theory, not deployed practice, so "degenerate form" doesn't map cleanly — the nearest equivalent is that pure TIME-DECAY was cognitive science's OWN earlier, now-superseded oversimplification, replaced by interference accounts precisely because decay-alone under-explains real forgetting. That is itself the useful warning: a governed-persistence layer that ages entries by clock alone is adopting the model the field already found insufficient.

**TOP 3 OVERALL, RANKED**
1. **Incremental materialized-view maintenance (Gupta & Mumick, axis C).** Strongest-evidence claim: a view can be kept correct via a DELTA/counting algorithm against the base-data change alone, never re-reading the full view or full source — this is the most directly implementable answer to "derived facts re-derived when upstream moves," and it's a formally studied algorithm, not a rule of thumb.
2. **CMDB discovery-driven reconciliation + authority-hierarchy federation (axis B, also answers Q4 below).** Strongest-evidence claim: "a CMDB without continuous automated discovery goes stale within weeks" — paired with the named counter-practice (federate into a CMS, each source tool is system-of-record for its domain, a configured authority hierarchy resolves disagreement automatically) — this is the field's own closest-scale failure/recovery pair.
3. **Appraisal-as-recurring-process / records continuum (axis A).** Strongest-evidence claim: ISO 15489:2016 explicitly reframes appraisal from a one-time keep/destroy decision into a process re-applied at multiple points in a record's life — directly validates governed-persistence's design instinct that admission and staleness are not settled once.

**CMDB-SPECIFIC (closest industrial-scale failure homolog)**
Root causes named by practitioners:
1. **Manual-entry drift**: "CMDBs drift the moment they're populated — manual entries miss changes, bulk imports duplicate CIs" — staleness starts at population, not later.
2. **No continuous discovery**: a CMDB not backed by an automated discovery platform "tends to go stale within weeks" — the record and the system it describes have independent update cadences and nothing keeps them synced.
3. **No real data-management ownership**: repeated failed CMDB projects (often 3-4 attempts) trace to no one with actual data-governance expertise running the effort — a tooling problem misdiagnosed as a technology problem.
Named countermeasure that measurably differs from the failure mode: **federation into a Configuration Management System (CMS)** rather than one monolithic database — each specialist tool (ITFM, SAM, discovery scanners) stays the system-of-record for its own domain and is REFERENCED rather than copied; when sources disagree, a **configured authority hierarchy** resolves the conflict automatically instead of by manual reconciliation. Sequence named for successful builds: discover → load & reconcile → certify accuracy → operate as a living (continuously re-discovered) source of truth, not a static snapshot.
